# 《FitNote 全域设计方案》评审意见

评审时间：2026-10-14 ｜ 对照物：FitNote 产品 brief v2、已产出的设计稿 v1（`docs/design/`）

## 总体判断

这份方案的水平明显高于常见的 UI 稿——它不只是"画得好看"，而是把**原则落到了可执行规则**（玻璃限定三类场景、警示色限额、点击只做 0.96 缩放）。方向我完全同意，**不需要推翻重做**。

问题集中在两类：**① 方案自己写下的标准，方案里的数值不满足**（颜色对比度）；**② 几处 iOS 惯例记反了，以及真实使用场景没覆盖到**。

---

## 先说做得好的（这几条请保留）

| 亮点 | 为什么好 |
|---|---|
| **隐私可视化**：启动页 / 录入页 / 导出页都标注「数据仅存本机」 | 这是把"隐私"从一个口号变成了界面上看得见的东西，且**可验证** |
| **离线可感知**：不做同步动画、不做网络失败提示 | 大部分 App 反着做（转圈、重试、离线横幅），这条是真正的逆向差异化 |
| **玻璃只限三类场景**（底部导航 / 底部固定主按钮 / 模态弹层） | 直接对应上次 UI 被批"廉价 AI 感"的根因：毛玻璃滥用。这条一立，观感立刻上一个档 |
| **单一强调色 + 灰度层级** | 同上，正确的纪律 |
| **强操作弱反馈、非必要不弹窗** | 工具型产品的正确取舍 |
| **警示色「全局不超过 3 处」** | 这个"限额"思维很专业（虽然表述需收紧，见 P2-13） |

## P0 —— 必须改（会翻车，或方案自相矛盾）

### P0-1｜颜色层级写反了：页面背景 ≠ 白色

方案写的是「页面背景 `#FFFFFF`、卡片背景 `#F2F2F7`」。这在 iOS 语境下是**倒过来的**：

- iOS 分组列表的真实层级：**页面底 `#F2F2F7`（浅灰）→ 卡片 `#FFFFFF`（白）**
- 你写的是：白底 + 灰卡 —— 卡片会变成"凹进去的槽"，尤其配合下一条"禁用投影"时更明显

**但这不是死错**，取决于你想要哪种：白底 + 浅灰块的风格（类似 Notion 的灰块）也成立。**需要你定一下**：

| | 方案 A（iOS 分组列表，推荐） | 方案 B（白底 + 灰块） |
|---|---|---|
| 页面背景 | `#F2F2F7` | `#FFFFFF` |
| 卡片背景 | `#FFFFFF` | `#F2F2F7` |
| 卡片边界 | 轻阴影（几乎看不见） | 必须靠描边，且会显"凹陷" |

### P0-2｜对比度自相矛盾：方案要求 ≥4.5:1，但 4 个色值都不达标

方案第七节写了「文本对比度 ≥4.5:1，满足 WCAG 2.1」。我按 WCAG 公式实算了方案第二节的色彩系统：

| 色值 | 用途 | 对白底实测对比度 | 判定 |
|---|---|---|---|
| `#1D1D1F` | 一级文本 | **16.8 : 1** | ✅ 优秀 |
| `#86868B` | 二级文本（副标题、说明） | **3.62 : 1** | ❌ 不达 4.5 |
| `#C7C7CC` | 三级文本（占位符） | **1.68 : 1** | ❌❌ 几乎看不清 |
| `#34C759` | 主色，用于「关键数据」文字 | **2.22 : 1** | ❌❌ 严重不足 |
| 白字放在 `#34C759` 按钮上 | 主按钮 | **2.22 : 1** | ❌ 不达 4.5 |

`#34C759` 是 iOS 系统绿，苹果自己用它做按钮底色配白字——但那是因为**大字号+粗体**才勉强可读；纯正文和白底上的绿色文字一定糊。

**修正建议（可直接替换）**：

| 角色 | 原值 | 改为 | 实测 |
|---|---|---|---|
| 二级文本 | `#86868B` | **`#6E6E73`** | 5.07 : 1 ✅ |
| 三级文本（占位/禁用） | `#C7C7CC` | **`#A1A1A6`** | 2.57 : 1（仅限占位符与禁用态，WCAG 对此豁免） |
| 强调色 · **文字/图标**（浅色） | `#34C759` | **`#1E7A34`** | 5.40 : 1 ✅ |
| 强调色 · **填充按钮** | `#34C759` + 白字 | `#34C759` + **深绿字 `#06371C`** | 6.02 : 1 ✅ |
| 强调色 · 深色模式 | — | `#3ED17F` | 对 `#0A0C0B` 是 9.9 : 1 ✅ |

> 一句话：**绿色可以留，但"绿底白字"要改成"绿底深绿字"，"白底绿字"要加深**。

### P0-3｜引导 8 步 + 滚轮"无默认选中"—— 这是最大的流失点

方案第三节：欢迎 → 出生日期 → 身高 → 体重 → 腰围 → 训练经验 → 计划推荐 → 祝贺，**8 步**；且滚轮「所有选项均为二级灰度，无高亮选中项，无预设数值」。

两个问题：

1. **用户在还没看到产品价值前，要滚 4 次空白滚轮**（生日 3 列 + 身高 + 体重 + 腰围），每项多花 5–10 秒。
2. **"停在中间但不显示选中"在交互上是反直觉的**——用户滚完松手，中心项是灰的，他不知道到底选中了没有。方案自己也写了"停止滚动 0.3 秒后过渡到主色高亮"，那其实**就已经是选中态了**，与"无高亮选中项"自相矛盾。

这条我在上一轮 brief 评审里提过，brief v2 已改成"给默认值 + 可跳过"，**这份方案又改回去了**。

**建议**：压到 **3 步**——① 欢迎+隐私承诺 ② 身体数据（预填 178/72.5/82，直接可下一步，也可改）③ 选计划模板。生日移到"我的 → 身体档案"里按需填（体脂率算法用的是年龄，不必在引导里问日期）。

### P0-4｜手势打架：同一个"左滑"被赋予三个含义

方案里出现了三处横向手势，语义互相冲突：

| 出现位置 | 手势 | 含义 |
|---|---|---|
| 第七节 · 转场动效 | 页面间**左右滑动** | 切换页面 |
| Tab2 · 列表区 | **左滑** | 编辑 / 删除记录 |
| Tab2 · 顶部切换栏 | **横向切换** | 训练 / 饮食 / 体脂 |

用户左滑一条训练记录，到底是删它、还是切到"饮食"标签、还是回上一页？

**建议按 iOS 真实边界划分**：

- **Tab 之间不滑动**（点选即可，iOS 原生 Tab 就不滑动切页）
- **分类标签可滑动**（那是分段控件，滑动合理）
- **列表行左滑 = 行内操作**（编辑/删除），严格限制在行内，不触发页面转场
- **返回 = 屏幕左边缘右滑**（`edge swipe`，只有 20px 热区）

### P0-5｜缺了产品最高频的那个界面：「记组」

整份方案第四节把四个 Tab 写得很细，但**没有一处描述"训练进行中"的界面**——你正在做的核心动作（记一组 60kg × 8）没有任何设计定义。

这是最容易翻车的地方：四 Tab 是"看数据"的界面，**记组是"产生数据"的界面**，后者才是日活来源。

我在设计稿 v1 里已经画了（`docs/design/dark-02-training.png`），要点是：重量 ±2.5kg 大型步进器、次数 ±1、**「上次 62.5kg × 8」始终可见**、组间倒计时、拇指区一键「完成本组」。**这一屏的规范必须补进方案。**

### P0-6｜假入口：「上传训练视频」v1.0 还不能用

今日页快捷操作卡里放了「上传训练视频」，但按 brief v2 的分期，视频识别是 **v1.1**。

界面上出现一个点了没反应（或弹"敬请期待"）的入口，是工具型产品最伤信任的事——尤其你的定位是"无冗余"。

**建议**：v1.0 该位置放「手动记训练」；视频入口等 v1.1 能用了再上。

## P1 —— 结构建议

### P1-7｜底部导航：49px 是旧 iOS 尺寸，配不上新材质

方案写「高度 49px，液态玻璃背景」。但 **49pt 贴底 tab bar 是 iOS 6–18 的形态**（无圆角、贴屏幕底边）；iOS 26 的新形态是**悬浮胶囊**（离底边有间距、大圆角、可收缩）。

"49px 贴底" + "液态玻璃滑动高光"是**两个时代的混搭**。二选一：

- 走 iOS 26 新形态 → 悬浮胶囊（高 62px，左右各 12px，距底 20px，圆角 26px）
- 走经典形态 → 贴底 49px，材质改成普通毛玻璃，不要滑动高光

我在设计稿里用的是前者。

### P1-8｜"四 Tab" 还是 "四 Tab + 中央凸起按钮"？

方案第五节写"四个 Tab 横向均分"，但没说中间那个凸起的主操作按钮在哪。

我们的设计稿是**四 Tab + 中央凸起「＋」**（共 5 个位置）。这直接影响"开始训练/快速记录"从哪进。**需要定死。**

### P1-9｜"一律禁用投影"会让浅色卡片边界不清

方案写「统一平面质感，无额外投影、浮雕；仅卡片自带 1px 极细描边」。

纯平面 + 无投影是好的方向，但**在浅色模式下，如果卡片底色和页面底色接近，只靠 1px 描边会显得"廉价"**（像线框稿）。

iOS 的实际做法是：白色卡片 + **几乎看不见的阴影**（`0 1px 2px rgba(0,0,0,.04)`）。这一层阴影**不是装饰**，它承担的是"卡片浮在页面之上"的语义。建议保留，但压到极轻。

### P1-10｜缺空状态与异常态（方案只写了成功路径）

方案里只在"Tab2 记录"写了空状态。但这些真实场景没有定义：

- **首次打开、零数据时的「今日」页**长什么样？（进度环 0%？还是换成引导）
- **识别出错**怎么改？（识别成"汉堡"其实是"三明治"）
- **模型加载失败**怎么降级？（还能不能手动记餐）
- **相机/相册权限被拒**怎么继续用？（引导去设置？还是退回手动选食物）
- **"当日目标进度环"的目标到底是什么**？（训练完成？热量达标？两者加权？—— 这个没定义，环就没法画）

### P1-11｜缺数据口径（不定义，开发时必然返工）

| 概念 | 待定义 |
|---|---|
| **训练容量** | 重量×次数？热身组算不算？自重动作（引体、俯卧撑）怎么计？ |
| **PR（个人记录）** | 按"最大重量"还是"估算 1RM"还是"最大单组容量"？去重规则？ |
| **组间计时** | App 切后台再回来，计时是否准确？（必须按时间戳算，不能用 setInterval 累加） |
| **连续记录天数** | 断一天算不算断？补记昨天的算不算？ |

## P2 —— 表述与细节

- **P2-12｜pt / px 混用**：字体用 `pt`（28pt/20pt/16pt），间距用 `px`（20px/16px/48px）。iOS 原生规范里都用 pt，但在我们的**单文件 HTML + WebView** 实现里应统一为 `px`（1x 下数值相同），否则开发时容易换算错。
- **P2-13｜"警示色全局不超过 3 处"** 表述模糊：是"3 个界面"还是"3 个元素"？实际"删除"会散落在记录/动作/食物多个列表里，必然超。建议改为**「仅用于破坏性操作确认与错误态，不得用于强调」**——用语义约束替代数字限额。
- **P2-14｜"最低支持 iOS 12" 与 "iOS 26 液态玻璃" 的关系**：液态玻璃是 iOS 26 的材质，iOS 12 上做不出来。而且我们当前实现是 **单文件 HTML + Android WebView 壳（开源）**，玻璃效果是 CSS 模拟的，**与系统版本无关**。这条需要明确：是要出 iOS 原生版，还是继续走跨平台 WebView？（后者的话，"SF Pro 字体"在安卓上只能回退到 HarmonyOS Sans / MiSans，"iOS 原生开关"要 CSS 模拟。）
