# FitNote Brief 评审意见

> 评审对象：《FitNote 产品Brief》（训练 + 体脂 + 饮食 + 计划 四合一）
> 评审角度：能否真的做出来 + 能否经得住第一次真实使用
> 结论：**方向对（离线自主 + 数据闭环 + 极简），但有 6 处必须改的硬伤、5 处结构性建议、4 处措辞修正。**

---

## 一、必须改（P0）——不改会在首次真实使用就被打穿

### P0-1 视频识别"重量"是不成立的承诺

- **原文**：「本地上传训练视频即可自动识别动作类型、**重量**、组数、次数」
- **为什么不行**：从视频读杠铃重量需要识别片数/片色/杆型，而拍摄角度、遮挡、光线完全不受控。Strong / Hevy / 训记全部靠手动，行业无可用方案。这是**技术不可行**，不是"难"。
- **改法**：范围收敛为 **动作类型 + 次数 + 组数 + 组间间隔**；重量改为 **记忆上次 + ±2.5kg 步进 + 片重预设**（一次录入后基本不用再改）。
- **收益**：承诺从"可能翻车"变成"稳定兑现"，且重量步进本来就比视觉识别更快。

### P0-2 "自主研发训练动作识别模型"是高成本 + 可信度双风险

- **为什么**：自研动作识别模型需要数千段带标注训练视频 + 标注体系 + 训练/调参/端侧量化，是数月量级的工程，个人或小团队极难覆盖；且公开宣称"自研模型"容易被追问数据集来源与评测结果。
- **改法**：措辞与实现都改为 **"开源视觉底座（姿态估计，如 MoveNet / MediaPipe Pose）+ 自研判定层（动作规则、计数算法、组数切分）"**。真正自研且真正值钱的是**判定逻辑**，不是底层网络。这既省掉数月工作，也更好对外讲。

### P0-3 "数据加密存储于设备本地"——过度承诺

- **为什么**：当前架构是 localStorage 明文。若真要加密，密钥存哪？存本机等于把钥匙和锁放一起；用用户口令派生则**忘记口令 = 数据全丢**，与"零门槛"直接冲突。
- **改法**：改成可验证的表述——**"仅存于本机、不上传；可手动导出备份；可一键清空"**。别用"加密"这个词，除非真做且接受上述取舍。

### P0-4 "模型加载 0.5s、推理 60ms" 是两条不同管线的数字

- **为什么**：现有实测数字来自**食物识别**（单张 224×224，模型加载 0.5s、单次推理 60ms）。**动作识别是视频管线**：30 秒视频抽帧 8–12fps ≈ 240–360 帧，逐帧姿态估计，不可能 60ms。混写会被技术方一眼看穿。
- **改法**：拆成两行分别给目标：
  - 食物识别：加载 ≈0.5s，单张推理 ≈60ms
  - 动作识别：30 秒视频**目标 ≤8 秒**（抽帧 + 姿态 + 计数），显示进度、可取消

### P0-5 首次引导 6 步 + "均无默认选中值" = 自我加难的漏斗

- **为什么**："无默认占位、分步递进"听起来严谨，实际是**用户在没看到产品前必须滚完 4 项数据的空白滚轮**（生日 3 列 + 身高 + 体重 + 腰围）。空滚轮从零开始滚，每项多花 5–10 秒，是典型的高流失点。这与"零门槛/轻量化"的定位自相矛盾。
- **改法**：
  1. **给合理默认值**（如身高 170 / 体重 65 / 生日 1995-01-01），用户只需微调甚至直接下一步；
  2. **允许跳过**：身高体重腰围可只填身高体重（围度法需要腰围，可后补）；
  3. **导览压到 3 步内到首页**：欢迎+隐私承诺 → 身体数据（预填） → 训练经验；三档计划**放到首页一键采用**，而不是必须走完才进 App；
  4. 保留"完成祝贺页"作为**可跳过**的收尾，别挡路。

### P0-6 动态调整规则"全自动"会让用户觉得计划不受控

- **原文**："当日缺练自动拆分训练量至次日""连续不达标则简化饮食方案""训练过量+饮食不足时自动降强度加热量"
- **为什么**：用户第二天打开看到计划变了却不知道为什么，会炸。自动化越强，**可见性**就必须越强，否则从"智能"变成"乱改"。
- **改法**：所有调整都是 **"建议 + 一键确认"**，并在「今日」页用一句话说明原因与结果，例如：
  > 昨天腿部训练未完成 → 建议今日补 2 组深蹲（已为你排在训练首位）　［采纳］［忽略］
  同时提供"本周不再自动建议"开关。

## 二、结构性建议（P1）——方向对但结构需要收敛

### P1-1 定位与功能不自洽：说要"普通人群"，做的却是"进阶工具"

- **矛盾点**：核心用户写"普通人群"，但功能体系是围度法、训练容量、PR、肌群占比、训练经验三档——这些是进阶用户语言。普通人看到"容量/PR"就退出了。
- **改法**：二选一，别含糊。
  - 若面向普通人：砍掉容量/PR/肌群占比，只留"练了什么 + 今天消耗多少"；
  - 若面向进阶（**我建议这条**）：核心用户改为"有固定训练习惯、会自己安排计划的进阶者"，普通人作为跟随者通过"三档计划"进入。这样功能与人群一致，也和你上一版 brief 的定位对齐。

### P1-2 四 Tab 里"记录"会变成三合一表单

- **为什么**：训练/饮食/体脂三套录入都塞进「记录」，这个 Tab 必然要做成"先选类型再填表"的分叉入口，直接违反"核心功能 ≤2 步"。
- **改法**：
  - **今日** = 情境化入口（晨间引导记早餐、训练时段引导记训练）+ 进度；
  - **记录** = **时间线与历史**（今天/本周做了什么，可点进去改），不是录入大厅；
  - **录入主动作**放在中央凸起按钮：按当前时间智能默认（饭点→拍照识餐，其他→记训练），长按可选另一项。

### P1-3 首版范围过大，建议分三期（否则发不出来）

| 版本 | 内容 | 目的 |
|---|---|---|
| **v1.0** | 体脂测算 + 饮食追踪（拍照识餐 + 食物库 + 三餐记账）+ 简化训练记录（手动、极速）+ 数据看板 + 导出 | 先让"记录"这件事跑通并可日常使用 |
| **v1.1** | 离线视频识别（动作 + 次数/组数） | 上差异化核心 |
| **v1.2** | 计划生成 + 动态调整联动（建议式）+ 周报 | 上闭环 |

> 理由：视频识别和动态计划是**最难且最容易被感知为"没做好"**的两块；先把"每天愿意打开"做扎实，再上亮点。

### P1-4 缺竞品分析（这版删掉了，反而更弱）

- 对外沟通必须有对照。建议保留一张表：**训记 / Strong / Hevy / Keep**，每个只写"它的强项 + 我们的切口"（记录步数、离线、无会员、中文动作库与统计口径）。

### P1-5 北极星口径太松，会自我虚高

- **原文**："7日留存（连续7天完成1次训练记录**或**3餐饮食记录）"
- **问题**："或"让口径模糊，记 1 餐是否算？跨周怎么算？
- **改法**：明确为——**连续 7 天内，每天至少完成 1 次有效记录（训练 ≥1 组，或 记餐 ≥2 餐）**；并补效率指标 **单动作记录耗时中位数 <25 秒**（这是本产品最该守住的体验红线）。

## 三、措辞与一致性修正（P2）

| # | 原文 | 问题 | 建议 |
|---|---|---|---|
| P2-1 | "零出网请求（目标值 0）" | 与"可配云端兜底/可选 AI"冲突；一旦用户填了密钥就矛盾 | 改为：**默认路径 0 出网；仅当用户主动配置第三方密钥后才会联网，且可随时关闭** |
| P2-2 | "全本地数据存储…支持手动导出备份" | 没提**换机/丢手机**这一最大数据风险 | 补：首启提示备份；提供"导出到下载目录"与"从文件恢复"；建议每 7 天提醒一次 |
| P2-3 | "极致极简…仅必要位置使用玻璃效果" | 方向正确，但没给判定标准，落地会走形 | 补一句硬约束：**玻璃只允许出现在吸顶导航 / 底部标签 / 弹层 / Toast；内容区一律实心表面 + 发丝分隔线** |
| P2-4 | "最低支持安卓 6.0 / 网页版单文件运行" | 没写包体与性能红线 | 补：**APK ≤15MB（含模型）；冷启动 ≤1.5s；识别相关模型一律按需加载** |

## 四、可加分的两处空白（建议补进 brief）

1. **数据模型**：`Exercise / Session / SetEntry / MealLog / BodyRecord / Plan / PR` 七个实体与字段。上一版训练记录 brief 已给出前四个，合并时可直接并入。
2. **失败路径**：识别错了怎么办（一键修正 + 撤销）、模型加载失败怎么办（降级为手动选择）、无视频权限怎么办。**只写成功路径的 brief，开发时必然反复返工。**

---

## 五、一句话总结

> 这份 brief 的问题不在"想法"，而在**三处过度承诺（重量识别 / 自研模型 / 加密存储）**、**一处自我加难（引导流程无默认值）**、**一处自动化过强（计划自动改）**，以及**首版范围过大**。
> 把这三类改掉、范围分三期，这份 brief 就是可直接进入开发的规格书。

*评审意见供决策参考，不改变你的产品方向。*
